# 后端治理总览

本文档记录当前后端治理阶段的收口状态，作为后续业务功能开发时的边界参考。当前策略从“持续拆分”切换为“按业务触达小步治理”：不再按行数硬拆服务，只在新增功能、修复问题或明确低风险时做最小清理。

## 总体状态

- 当前治理完成度：约 90%。
- 已完成主线：接口自动化、execution、bug、AI、用例中心、settings、workspace、user、auth。
- 主要成果：Controller 调用路径保持不变，核心 Service 逐步门面化，领域逻辑下沉到 DomainService / Support，关键链路补充接口或 service 级回归测试。
- 当前收口结论：后端结构已经可以支撑继续业务开发，暂不建议继续开启大范围纯重构。

## 暂不继续清理的原因

- 项目仍在开发中，继续大拆会提高后续功能合并成本。
- 当前剩余大类多是业务聚合点，不是单纯坏味道；按行数拆分收益有限。
- 已有测试和文档足够支撑后续业务迭代。
- 对仍在演进的模块，应在功能触达时顺手治理，而不是单独做大范围结构重排。

## 后续开发规则

1. Controller 继续保持入口层，只做参数接收、基础校验和调用 Service。
2. Service 优先保持门面职责，业务主逻辑放在 DomainService，通用纯逻辑放在 Support。
3. 不新增数据库结构、接口路径或响应结构，除非业务目标明确要求。
4. 新功能优先沿用当前模块已有命名、异常、权限和测试组织方式。
5. 每次改动只覆盖当前目标范围，不顺手重构无关模块。
6. 对外部 AI、文件、SSE、异步任务等链路，优先 mock 外部依赖，保护确定性行为。
7. 发现无调用代码可以小步删除，但必须先全仓检索，并运行相关回归和 compile。
8. 不按行数继续拆类；只有职责边界清楚、测试保护足够、风险低时才拆。

## 功能开发前建议

- 开始新业务前，先确认涉及模块和已有 DomainService / Support 边界。
- 若新增接口，先确定是否需要接口级回归测试。
- 若修改筛选、分页、权限、状态流转、附件、异步任务或 AI 调用链路，必须补匹配测试。
- 若功能涉及前后端联调，优先保持后端兼容旧参数和旧响应，再做前端最小接入。
- 每个较大功能完成后补一份简短回归记录，方便后续继续治理或排查问题。

## 下一阶段建议

后端治理阶段到此收口。下一阶段建议切回业务功能开发：由具体功能目标驱动后端小步治理、测试补齐和前端联调，不再单独推进大范围后端拆分。
